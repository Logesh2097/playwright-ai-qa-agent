# Test Reports and Evidence Management

What is kept from a test run, who can get at it, how a report is built and
exported, and how history, comparison, trends and the dashboard are computed
(Phase 10).

Two rules hold throughout:

- **Every figure is counted from the stored results when it is asked for.**
  Nothing is copied from an earlier report, and no model output is read to
  produce a number or a status.
- **Evidence never has a public address.** A file leaves only through the API,
  after the same checks as any other request.

## 1. Evidence

| Evidence | How it is kept |
|----------|----------------|
| Screenshots | PNG files. On failure by default, or after every step (`evidence.screenshots: always`). Fields that hold a secret are painted over |
| Browser video | WebM, optional (`evidence.video`) |
| Playwright trace | Zip, optional (`evidence.trace`) |
| Console log | JSON file of every console message and uncaught page error of an attempt. Error lines are also kept with the result |
| Network errors | JSON file of failed and blocked requests. Also kept with the result |
| Step outputs | With each step: action, locator used, values read, page address |
| Assertion details | With each step: expected, found, error type and message |
| Timestamps | Start, end and duration of the execution, each result and each step |

Capture is configured per execution (`config.evidence`); each of
`screenshots`, `video`, `trace` and `logs` is `off`, `on_failure` or `always`.
Defaults: screenshots and logs on failure, video and trace off. A log file is
not written when the browser reported nothing.

Video and trace are not recorded for a case that types a secret itself, as
before ([test-execution-engine.md](test-execution-engine.md) §9).

## 2. Storage

`app/services/evidence.py` defines `EvidenceStorage` (put, read, chunks,
delete, delete an execution, list organizations). One implementation exists,
`EvidenceStore`, on a directory (the `evidence` volume: written by the worker,
mounted read-only in the API). An object store would implement the same
methods; `evidence_storage(settings)` is the one place that chooses.

For any implementation:

- a storage key is generated by the store (`{organization}/{execution}/{random}.{ext}`)
  and never taken from a request;
- a key is only resolved inside the branch of the organization asking, so a
  key of another organization, or one that walks up the tree, finds nothing.

### What is accepted

Before a file is stored (`validate`):

| Check | Rule |
|-------|------|
| Kind | One of screenshot, video, trace, console_log, network_log |
| Content type | The one type of that kind (PNG, WebM, zip, JSON) |
| Content | Starts with that format's signature; JSON must parse to an object or list |
| Size | Screenshot 10 MB, video or trace 100 MB, log 1 MB (`EVIDENCE_MAX_*_BYTES`) |
| Execution quota | All files of one execution together: 1 GB (`EVIDENCE_MAX_EXECUTION_BYTES`) |

A file that fails a check is not stored. The result is unaffected and records
why in `details.evidence_notes` (for example `screenshot_not_stored:invalid_content`).

### Redaction

- Everything the engine sends passes its redactor first: the values of secrets
  the run was given, in plain and common encoded forms.
- Log files are redacted again when written: bearer and basic tokens, JSON web
  tokens, cookie and authorization headers, sensitive URL parameters. They are
  stored with `redaction_status: applied`.
- Screenshots mask secret fields. Video and trace are skipped for cases that
  type a secret.
- A file marked `failed_quarantined` is never served.

Images and recordings cannot be searched for sensitive text. What an
application shows on screen is in its screenshots; that is why access is
restricted and retention is limited.

### Retention

| Kind | Kept | Setting |
|------|------|---------|
| Screenshots, logs | 30 days | `EVIDENCE_RETENTION_DAYS` |
| Video, trace | 14 days | `EVIDENCE_RECORDING_RETENTION_DAYS` |

`expires_at` is set when a file is stored. Past it, the file is refused to
every reader at once and left out of reports. An hourly worker job
(`prune_evidence`) then deletes the file and its record, organization by
organization inside each one's row-level security scope. Results, steps and
reports are kept; a report notes how many files are no longer available.

## 3. Access

| Level | How it is enforced |
|-------|--------------------|
| Organization | Membership is checked on every request; every query is scoped to the organization and row-level security applies underneath. The store resolves keys inside the organization's branch only |
| Project | The caller must be a member of the project (or an organization admin). Others get 404 |
| Execution | A file is looked up within the execution in the address. An evidence ID of another execution gives 404 |

Reading is allowed to project members, viewers included. Starting executions
is not.

Files are served as attachments with `X-Content-Type-Options: nosniff`,
`Cache-Control: private, no-store`, `Referrer-Policy: no-referrer` and a
sandboxing `Content-Security-Policy`, so a file is never rendered as a page of
the platform.

### Download addresses

`POST …/executions/{id}/evidence/{evidence_id}/download-url` returns an address
for one file, for browsers (a download link, a video player):

- the token names the organization, project, execution, file, user and sign-in
  session, is signed with the server's key and is valid for 5 minutes
  (`EVIDENCE_URL_TTL_S`, 30 s to 1 hour);
- redeeming it repeats every check as of that moment: the user is active,
  still in the organization, still sees the project, the session has not been
  signed out, and the file exists and has not expired;
- a sign-in token does not work as a download token, nor the reverse;
- issuing one is recorded in the audit log.

It is not a share link: it works only for the user it was issued to, while
that user keeps access.

## 4. Reports

`app/reporting/` holds one model of a report and its renderings:

| File | |
|------|--|
| `model.py` | `ExecutionReport`: what a report contains |
| `builder.py` | Stored rows → `ExecutionReport`. `assemble` is a pure function |
| `exports.py` | `ExecutionReport` → JSON, CSV, PDF |
| `analytics.py` | History, comparison, trend and dashboard figures. Pure functions |

A report contains: project, application, environment, testing instruction (for
executions started by the agent workflow), test suite, execution ID, start and
end time, duration, who started it, the totals (total, passed, failed, skipped,
blocked, error, flaky, needs review, pass rate), failure categories, a failure
summary per failed or errored case (failed step, expected, found, screenshots),
every result with its steps and evidence, AI-generated suggestions, and the
final status (the execution's verdict).

- Totals come from the same function that decides the verdict
  (`app/testing/verdicts.py`), so a report cannot disagree with its execution.
- **Pass rate** is passed ÷ cases that ran to an end (passed, failed, error,
  flaky, needs review). Skipped and blocked cases are in no rate. Flaky and
  needs-review results are not passes. With nothing run the rate is absent,
  not 0% or 100%.
- An AI suggestion is carried as written, with `advisory: true` and the note
  "AI-generated suggestion. Not a confirmed root cause, and it does not affect
  any status." in every format.
- Expired and quarantined evidence is left out and counted in a note.
- A report of an unfinished execution says it is provisional.

### Formats

| Format | Where | Content |
|--------|-------|---------|
| Web | `/projects/{id}/executions/{execution_id}` in the web application | The report, with steps per case, screenshots on request, exports |
| JSON | `GET …/report`, or `…/report/export?format=json` as a file | The report itself |
| CSV | `…/report/export?format=csv` | One row per test case result, UTF-8 |
| PDF | `…/report/export?format=pdf` | Summary, all cases, a section per case that did not pass with its steps, errors, suggestion and up to 12 screenshots |

Text that came from the application under test is treated as data in every
format: the web page places it as text only; a CSV cell that would start a
spreadsheet formula (`=`, `+`, `-`, `@`) is prefixed with `'`; the PDF writes
plain text. Exports are recorded in the audit log.

Reports are generated on request and not stored, so they always reflect the
current data. The report the agent workflow stores at the end of a run
([agent-workflow.md](agent-workflow.md)) is a separate record of that run.

## 5. History

| Question | Endpoint | Page |
|----------|----------|------|
| What ran? | `GET …/execution-history` — filters: `status`, `verdict`, `environment_id`, `suite_id`, `since`, `until`; `limit` ≤ 200, `offset`; answers with `total` | Execution history |
| What happened in one run? | `GET …/executions/{id}/report` | Test report |
| How has one case done? | `GET …/test-cases/{id}/history` | Result history |
| What failed lately? | `GET …/failures?days=` | Execution history, lower section |
| What changed between two runs? | `GET …/execution-comparison?base=&target=` | Comparison |
| How is it going over time? | `GET …/trends?days=` | Dashboard chart |

Comparison, per test case:

| Change | Meaning |
|--------|---------|
| `regressed` | Was not a failure, now failed or error |
| `fixed` | Failed or error, now passed |
| `still_failing` | Failed or error in both |
| `changed` | Any other difference (for example passed → flaky; failed → flaky is not a fix) |
| `added`, `removed` | In only one of the two |
| `unchanged` | Same result |

The answer says whether both executions ran in the same environment.

Trends give one point per UTC day, days without executions included with zero
executions and no rate.

## 6. Dashboard

`GET …/dashboard?days=` (1–180, default 30), all for the chosen period:

| Figure | Definition |
|--------|------------|
| Total executions | Executions started in the period |
| Pass rate | Passed ÷ case results that ran to an end |
| Failure rate | (Failed + error) ÷ case results that ran to an end |
| Executions fully passed | Executions with verdict `passed` ÷ finished executions |
| Flaky test count | Cases the rules of [result-validation-and-healing.md](result-validation-and-healing.md) §6 find flaky |
| Average execution duration | Mean of finish − start over finished executions |
| Frequently failing | Up to ten cases by number of failed or errored results, with runs, failure rate, usual category, last result |
| Recent executions | The last ten |
| Test coverage indicators | Test cases; approved; automated (approved with a script); run in the period; passing at last run — each with its share |

**The coverage indicators are about test cases, not code.** No code
instrumentation is integrated, so nothing here is, or is called, code
coverage; the API answer and the page both say so.

At most 20,000 rows are read for a period; if a period holds more, the answer
has `truncated: true` and the page says so.

## 7. Web pages

| Page | Route |
|------|-------|
| Dashboard | `/projects/{id}/dashboard` |
| Execution history, failed tests | `/projects/{id}/executions` |
| Test report | `/projects/{id}/executions/{execution_id}` |
| Comparison | `/projects/{id}/executions/compare?base=&target=` |
| Result history of a case | `/projects/{id}/cases/{case_id}/history` |

Only `passed` is shown in green; flaky, needs review and inconclusive are
amber. The trend chart shows one series (pass rate per day), breaks its line on
days when nothing ran, can be read with the arrow keys and has a table view.
Screenshots are fetched with the session when asked for and shown only as
images.

## 9. Known limitations

- **One storage implementation** (a directory). The interface is ready for an
  object store; none is included.
- **Retention is per installation**, by kind. There is no per-project setting
  and no legal hold.
- **Screenshots and recordings are not scanned** for sensitive content.
- **Reports are not stored.** A report of an old execution is rebuilt from
  current data and omits evidence that has expired.
- **PDF uses built-in fonts**: characters outside Latin-1 are replaced by `?`.
  JSON and CSV keep them.
- **No HTML file export, JUnit export or share links.**
- **History figures are computed on request** from up to 20,000 rows, without
  pre-aggregation.
- **A download address can be used more than once** within its few minutes, by
  anyone who has it and only while its user keeps access.
- **Pages cover reporting only.** Starting executions, heal proposals and
  workflows are still API only.
