# API Design

REST over HTTPS, JSON, base path `/api/v1`. The OpenAPI document generated by FastAPI is the contract; frontend types are generated from it.

## 1. Conventions

### 1.1 Authentication

| Caller | Mechanism |
|--------|-----------|
| Browser (SPA) | `Authorization: Bearer <access JWT>` (15 min). Refresh token in an HttpOnly, Secure, SameSite=Strict cookie scoped to `/api/v1/auth`. See §2. |
| CI / scripts | `Authorization: Bearer qak_<key>` — API key with scopes, optionally bound to one project. |
| GitHub | Webhook signature (`X-Hub-Signature-256`) verified against the app's webhook secret. |
| SSE | One-time ticket from `POST /executions/{id}/stream-ticket`, passed as a query parameter (EventSource cannot send headers). |

The active organization is part of the path for organization-level resources and is derived from the resource for everything else. Membership and role are checked on every request.

### 1.2 Roles

Implemented in `app/core/security/permissions.py`. Checks are made against permissions; a role is a named set of them. Roles are read from the database on every request, so a role change or removal takes effect on the next call.

| Role | Can |
|------|-----|
| `viewer` | Read everything in the organization except secrets and audit logs. |
| `developer` | + submit instructions, edit cases, run on non-production environments. *(test permissions arrive with their features)* |
| `qa_engineer` | + approve plans/cases/heal proposals, manage suites, run with approval on production. *(as above)* |
| `admin` | + rename the organization, manage members and invitations, read audit logs, manage projects, applications, environments, credentials, integrations and MCP connections; approve production runs. |
| `owner` | + delete the organization; the only role that can grant or remove `owner`. |

Rules that apply to every role:

- Nobody can grant, change or remove a role above their own (`viewer` < `developer` < `qa_engineer` < `admin` < `owner`).
- An organization always keeps at least one active owner.
- A caller who is not an active member of the organization in the path receives **404**, exactly as for an organization that does not exist.

### 1.3 Errors

All errors use one envelope (`application/problem+json`):

```json
{
  "type": "https://docs.example/errors/validation_error",
  "title": "Validation failed",
  "status": 422,
  "code": "validation_error",
  "detail": "base_url must use https",
  "errors": [{ "field": "base_url", "code": "invalid_scheme", "message": "must use https" }],
  "request_id": "01JD..."
}
```

| Status | `code` examples |
|--------|-----------------|
| 400 | `bad_request`, `invalid_cursor` |
| 401 | `unauthenticated`, `token_expired`, `invalid_api_key` |
| 403 | `forbidden`, `insufficient_role`, `approval_required` |
| 404 | `not_found` (also returned for resources in other organizations) |
| 409 | `conflict`, `invalid_state_transition`, `duplicate`, `idempotency_mismatch` |
| 422 | `validation_error`, `url_not_allowed`, `origin_not_allowlisted` |
| 429 | `rate_limited`, `concurrency_limit`, `budget_exceeded` |
| 502/503 | `runner_unavailable`, `llm_unavailable` |

Error messages never include secrets, stack traces, or internal hostnames.

### 1.4 Common behaviour

- **Pagination**: `?limit=50&cursor=<opaque>`; response `{ "items": [...], "next_cursor": "..." | null }`. Max limit 200.
- **Filtering/sorting**: explicit query parameters per endpoint; `sort=-created_at`.
- **Idempotency**: `Idempotency-Key` header accepted on all `POST`s that create executions or instructions; replays return the original response.
- **Concurrency**: mutable resources return `ETag`; updates accept `If-Match` and fail with 409 on mismatch.
- **Rate limits**: per user, per API key, and per IP for auth endpoints. `Retry-After` on 429.
- **Validation**: Pydantic models with `extra="forbid"`; string length limits on every field; UUIDs validated in paths.
- **Long operations** return `202 Accepted` with the resource in a pending state; clients poll or subscribe.

## 2. Authentication

Status: **implemented (Phase 2).** Schemas are in the generated OpenAPI document at `/api/docs`.

**Token strategy.** `login`, `register` and `password/change` return a short-lived access token (JWT, 15 minutes) in the body and set a refresh token as a cookie: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. The web app keeps the access token in memory only. A refresh token works once; `refresh` rotates it. Presenting an already-used refresh token ends the whole session. Endpoints that read the cookie (`refresh`, `logout`) require an `X-Requested-With` header as CSRF protection.

| Method | Path | Auth | Success | Description |
|--------|------|------|---------|-------------|
| POST | `/auth/register` | — | 201 `Session` | Create a user and either a new organization (caller becomes owner) or, with `invite_token`, a membership in the inviting organization. Signs in. |
| POST | `/auth/login` | — | 200 `Session` | Email + password. |
| POST | `/auth/refresh` | cookie + `X-Requested-With` | 200 `Token` | Rotate the refresh token; new access token. |
| POST | `/auth/logout` | cookie + `X-Requested-With` | 204 | End this session. Its access tokens stop working immediately. |
| POST | `/auth/logout-all` | bearer | 204 | End every session of the user. |
| GET | `/auth/me` | bearer | 200 `Me` | Current user and memberships. |
| POST | `/auth/password/change` | bearer | 200 `Session` | Requires the current password. Ends every session and returns a new one. |
| POST | `/auth/password/forgot` | — | 202 | Always 202, whether or not the email is registered. |
| POST | `/auth/password/reset` | — | 204 | Single-use token from the reset email. Ends every session. |
| POST | `/auth/invitations/accept` | bearer | 204 | Join an organization. The account's email must match the invited address. |

```jsonc
// POST /auth/register          (exactly one of organization_name / invite_token)
{ "email": "qa@acme.io", "password": "correct horse battery staple", "full_name": "Asha Rao", "organization_name": "Acme" }

// 201 Session   (+ Set-Cookie: qa_refresh_token=…; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth)
{
  "access_token": "eyJ…", "token_type": "bearer", "expires_in": 900,
  "user": { "id": "…", "email": "qa@acme.io", "full_name": "Asha Rao", "is_active": true, "created_at": "…", "last_login_at": null },
  "memberships": [ { "organization_id": "…", "organization_name": "Acme", "organization_slug": "acme", "role": "owner" } ]
}

// POST /auth/login
{ "email": "qa@acme.io", "password": "…" }                       // 200 Session

// POST /auth/refresh            (no body)
{ "access_token": "eyJ…", "token_type": "bearer", "expires_in": 900 }   // 200 Token

// POST /auth/password/change
{ "current_password": "…", "new_password": "…" }                 // 200 Session

// POST /auth/password/forgot
{ "email": "qa@acme.io" }                                        // 202 { "status": "accepted" }

// POST /auth/password/reset
{ "token": "…from the email…", "new_password": "…" }             // 204
```

**Password policy.** 12–128 characters; no composition rules; rejected if it is a known common password, a trivially repeated pattern, or contains the user's name or email. Violations return 422 `weak_password` with one entry per reason in `errors[]`.

**Errors**

| Status | `code` | When |
|--------|--------|------|
| 400 | `csrf_header_missing` | `refresh` / `logout` without `X-Requested-With`. |
| 400 | `wrong_password` | `password/change` with an incorrect current password. |
| 400 | `invalid_reset_token` | Reset token unknown, used, superseded or expired. |
| 400 | `invalid_invitation` | Invitation unknown, expired, cancelled, or sent to a different email. |
| 401 | `invalid_credentials` | Unknown email, wrong password and deactivated account — identical response for all three. |
| 401 | `unauthenticated` / `invalid_token` / `token_expired` / `session_revoked` | Problems with the access token. |
| 401 | `invalid_refresh_token` | Refresh cookie missing, unknown, expired or already used. |
| 409 | `email_taken` | Registering an existing email. |
| 409 | `already_member` | Accepting an invitation to an organization the user is already in. |
| 422 | `weak_password`, `validation_error` | Policy or schema violation. Submitted values are never echoed. |
| 429 | `account_locked` | Too many failed sign-ins for this email (default 5 in 15 minutes). `Retry-After` is set. |
| 429 | `rate_limited` | Per-address limits on login, registration and reset requests. |

Known limitation: `register` answers 409 for an existing email, which reveals that the address is registered. Removing that signal requires email verification, which needs a mail transport (open question Q5).

## 4. Projects, applications, environments, credentials

Status: **implemented (Phase 3).** Schemas are in the generated OpenAPI document at `/api/docs`.

**Paths are nested under the organization and the project.** Row-level security needs the organization before any row can be read, and loading each level through its parent means an ID from another project, environment or tenant is simply not found. The base for everything below is

```
/organizations/{org_id}/projects
```

### 4.1 Who can do what

Access to a project needs **project membership**, except for organization admins and owners, who can reach every project. Membership only grants access; what a member may change is decided by their organization role. A project member with the project role `manager` can additionally edit the project and its member list.

| Action | viewer | developer / qa_engineer | admin / owner |
|--------|:---:|:---:|:---:|
| See projects they belong to; read applications and environments | ✔ | ✔ | ✔ (all projects) |
| Create a project (creator becomes manager) | | ✔ | ✔ |
| Edit, archive, restore a project; manage its members | | as project manager | ✔ |
| Delete a project | | | ✔ |
| Register, edit, delete applications | | ✔ | ✔ |
| Add, edit, delete non-production environments; run access checks | | ✔ | ✔ |
| Create or change **production** environments; enable `allow_private_network` | | | ✔ |
| See credential metadata; store, rotate, delete non-production credentials | | ✔ | ✔ |
| Manage production credentials | | | ✔ |

A project the caller cannot see answers **404**. An archived project is read-only: every write below it answers 409 `project_archived`.

### 4.2 Projects

| Method | Path (after the base) | Success | Description |
|--------|------|---------|-------------|
| GET | `` | 200 `Project[]` | Projects the caller can see. |
| POST | `` | 201 `Project` | `{ name, description? }` |
| GET | `/{project_id}` | 200 `Project` | |
| PATCH | `/{project_id}` | 200 `Project` | `{ name?, description? }` |
| POST | `/{project_id}/archive` · `/restore` | 200 `Project` | |
| DELETE | `/{project_id}?confirm_name=` | 204 | Safeguards below. |
| GET | `/{project_id}/members` | 200 `ProjectMember[]` | |
| POST | `/{project_id}/members` | 201 `ProjectMember[]` | `{ user_id, role: "member" \| "manager" }` — must be an active organization member. |
| PATCH | `/{project_id}/members/{user_id}` | 200 `ProjectMember[]` | `{ role }` |
| DELETE | `/{project_id}/members/{user_id}` | 204 | Managers remove others; anyone may leave. |

```jsonc
// Project
{ "id": "…", "organization_id": "…", "name": "Web Shop", "slug": "web-shop", "description": "…",
  "status": "active", "created_by": "…", "created_at": "…", "updated_at": "…",
  "member_count": 3, "application_count": 2, "my_role": "manager", "can_manage": true }
```

**Delete safeguards.** All must hold, otherwise nothing is deleted: the caller is an admin or owner; the project is archived (409 `project_not_archived`); `confirm_name` equals the project's name exactly (422 `confirmation_mismatch`); no test is running (409 `project_has_active_executions`). Deletion is a soft delete of the project, its applications and environments, and a **hard** delete of their stored credentials.

### 4.3 Applications

`…/{project_id}/applications` (GET list, POST) and `…/applications/{application_id}` (GET, PATCH, DELETE).

```jsonc
// POST …/applications
{
  "name": "Storefront",
  "description": "Customer-facing shop",
  "base_url": "https://shop.acme.io",
  "type": "web",                          // web | api
  "framework": "Vue 3 + Laravel",         // free text, optional
  "auth_method": "form_login",            // none | form_login | basic_auth | bearer_token | api_key | sso | other
  "default_browser_config": { "browser": "chromium", "viewport": { "width": 1440, "height": 900 }, "locale": "en-IN" },
  "allowed_domains": ["acme.io"]          // defaults to the host of base_url
}
// 201 Application: the same fields plus id, project_id, status (active | archived), environment_count, timestamps
```

`allowed_domains` is the outer boundary for the application: each entry covers that host and its subdomains, and every environment URL and allowed origin must fall inside it. Entries are plain host names — no wildcards, paths or single-label names. Narrowing the list is refused (422 `domain_in_use`) while an environment still uses a host it would no longer cover.

### 4.4 Environments

`…/applications/{application_id}/environments` (GET list, POST) and `…/environments/{environment_id}` (GET, PATCH, DELETE).

```jsonc
// POST …/environments
{
  "name": "Staging",
  "kind": "staging",                      // local | development | testing | staging | production | other
  "base_url": "https://staging.shop.acme.io",
  "api_base_url": "https://api.staging.shop.acme.io",
  "additional_origins": [ { "url": "https://auth.acme.io", "purpose": "auth_provider" } ],
  "variables": [ { "name": "FEATURE_LOYALTY", "value": "on" }, { "name": "API_TOKEN", "secret_ref": "api-token" } ],
  "auth_config": { "method": "form_login", "login_url": "https://auth.acme.io/login", "default_credential": "customer", "notes": "…" },
  "allowed_actions": ["navigate", "read", "click", "type", "select"],
  "is_read_only": false,
  "requires_approval": false,
  "allow_private_network": false
}
// 201 Environment
{ "id": "…", "application_id": "…", "name": "Staging", "kind": "staging", "base_url": "…", "api_base_url": "…",
  "allowed_origins": [ { "origin": "https://staging.shop.acme.io", "scheme": "https", "host": "staging.shop.acme.io", "port": 443, "purpose": "app" }, … ],
  "variables": [ … ], "auth_config": { … }, "allowed_actions": [ … ],
  "is_read_only": false, "requires_approval": false, "allow_private_network": false,
  "status": "active", "credential_count": 0, "created_at": "…", "updated_at": "…" }
```

Rules:

- The environment's allowlist is exactly: the origin of `base_url`, of `api_base_url`, and each `additional_origins` entry. An origin is scheme + host + port; a subdomain or another port is a different origin.
- Every one of those URLs is validated when saved (§4.6). A failure names the field in `errors[].field`.
- `production`: admins only; https required; `is_read_only` and `requires_approval` default to true.
- `is_read_only` limits `allowed_actions` to `navigate`, `read`, `api_read` (422 `actions_conflict_read_only` otherwise).
- `variables` hold non-secret values. A plain value under a name that looks secret (`*TOKEN*`, `*PASSWORD*`, …) is refused (422 `secret_in_variable`); use `secret_ref` with the name of a credential of the same environment.
- `allow_private_network` can only be enabled by an admin and is written to the audit log.

### 4.5 Access check

`POST …/environments/{environment_id}/access-check` → 200

```jsonc
{ "reachable": true, "final_url": "https://staging.shop.acme.io/login", "status": 200, "duration_ms": 184,
  "error_code": null, "error": null,
  "hops": [ { "url": "https://staging.shop.acme.io/", "status": 302 }, { "url": "https://staging.shop.acme.io/login", "status": 200 } ] }

// a redirect that leaves the allowlist is not followed
{ "reachable": false, "error_code": "origin_not_allowlisted", "error": "https://evil.example is not in this environment's list of allowed origins.",
  "hops": [ { "url": "https://staging.shop.acme.io/", "status": 302 }, { "url": "https://evil.example/x", "status": null, "blocked_code": "origin_not_allowlisted", "blocked_reason": "…" } ], … }
```

Only status codes are reported; response bodies are never read or returned. Rate limited per organization (429).

### 4.6 URL validation

Applied when an environment is saved, on every hop of an access check, and — from Phase 6 — on every navigation the browser makes.

| Step | Rejects | `code` |
|------|---------|--------|
| Syntax | Schemes other than http/https; embedded credentials; whitespace, control characters, backslashes; malformed hosts; numeric host forms such as `2130706433` or `0x7f.1` | `invalid_scheme`, `credentials_in_url`, `invalid_url`, `invalid_host`, `https_required` |
| Application boundary | Hosts outside the application's `allowed_domains` | `domain_not_allowed` |
| Allowlist (run time) | Origins not on the environment's list, including redirect targets | `origin_not_allowlisted` |
| Address | Hosts that do not resolve; hosts where **any** resolved address is loopback, private, link-local, cloud metadata, or otherwise non-public | `host_not_resolvable`, `address_not_allowed` |

`allow_private_network` permits loopback and private ranges only. Link-local and metadata addresses (`169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254`, …) are refused regardless. IPv6 addresses that embed an IPv4 address (mapped, 6to4, NAT64, Teredo) are judged by the embedded address.

### 4.7 Credentials

`…/environments/{environment_id}/credentials` (GET list, POST) and `…/credentials/{credential_id}` (GET, PATCH, DELETE).

```jsonc
// POST …/credentials — a stored secret
{
  "name": "customer", "role_label": "customer", "kind": "username_password",
  "secret": { "username": "cust01@acme.io", "password": "…" },     // write-only
  "is_test_account": true,                                          // must be true
  "setup_instructions": "Has 500 loyalty points.",
  "login_recipe": [ { "action": "fill", "target": { "strategy": "label", "value": "Email" }, "args": { "value": "{{cred.username}}" } } ]
}
// POST …/credentials — a reference; the value never enters the platform's database
{ "name": "api-token", "role_label": "service", "kind": "secret_value", "external_ref": "env:STAGING_API_TOKEN", "is_test_account": true }

// 201 / 200 Credential — metadata only
{ "id": "…", "environment_id": "…", "name": "customer", "role_label": "customer", "kind": "username_password",
  "source": "stored", "field_names": ["password", "username"], "external_ref": null, "is_test_account": true,
  "setup_instructions": "…", "login_recipe": [ … ], "last_rotated_at": null, "created_at": "…", "updated_at": "…" }
```

| Kind | Required `secret` fields |
|------|--------------------------|
| `username_password`, `basic_auth` | `username`, `password` |
| `bearer_token` | `token` |
| `api_key_header` | `header_name`, `value` |
| `cookie` | `name`, `value` |
| `totp_secret` | `secret` |
| `secret_value` | `value` |

Guarantees:

- **No endpoint returns a secret value.** The response schema has no field for one; `secret` exists on input only. `PATCH` with `secret` replaces it (audited as `credential.rotate`).
- Stored secrets are encrypted before they reach the database (see [security-design.md](security-design.md) §5.1).
- `is_test_account` must be `true` (422 `test_account_required`); the database enforces it as well.
- `login_recipe` and `setup_instructions` are stored in clear, so a request whose recipe or instructions contain a secret value is refused (422 `secret_in_plain_text`). Use `{{cred.<field>}}` placeholders.
- A credential referenced by its environment's variables or `auth_config.default_credential` cannot be renamed or deleted (409 `credential_in_use`).
- Validation errors never echo submitted values.

`external_ref` currently supports `env:VARIABLE_NAME` (resolved by the test runner from its own environment, from Phase 6).

Audit actions added in this phase: `project.create|update|archive|restore|delete|member_add|member_role_change|member_remove`, `application.create|update|delete`, `environment.create|update|delete|access_check`, `credential.create|update|rotate|delete|use`.

## 5. Test instructions and requirement analysis

Status: **implemented (Phase 4).** Test-case generation from an approved plan is Phase 5.

Base: `/organizations/{org_id}/projects/{project_id}/instructions`

An instruction is plain-language text aimed at one application and one environment of the project. Submitting it returns at once with status `analysing`; the analysis runs in the worker. **Poll `GET …/{id}`** until the status is `analysed`, `needs_clarification` or `failed`.

| Method | Path (after the base) | Success | Who | Description |
|--------|------|---------|-----|-------------|
| POST | `` | 202 `Instruction` | developer+ | Submit and start the analysis. |
| GET | `?status=&limit=` | 200 `Instruction[]` | project members | Newest first. |
| GET | `/{id}` | 200 `Instruction` | project members | Analysis, readiness, open questions, usage. |
| PATCH | `/{id}` | 202 `Instruction` | author or manager | Change text, types or options; discards the analysis and starts a new one. |
| POST | `/{id}/analyse` | 202 `Instruction` | author or manager | Run the analysis again (after a failure, or for a fresh result). |
| POST | `/{id}/clarifications` | 202 `Instruction` | developer+ | Answer open questions; analysed again with the answers. |
| PUT | `/{id}/analysis` | 200 `Instruction` | author or manager | Replace the structured requirement by hand. Same schema, same checks; marked `human_edited`. |
| POST | `/{id}/validate` | 200 `Instruction` | developer+ | Repeat the readiness checks without calling the AI (e.g. after adding a credential). |
| POST | `/{id}/approve` | 201 `Plan` | qa_engineer, admin, owner; **admin+ for production** | Approve the requirement as the testing plan. |
| GET | `/{id}/plan` | 200 `Plan` | project members | Current plan. |
| POST | `/{id}/cancel` | 200 `Instruction` | author or manager | A running analysis discards its result. |

```jsonc
// POST …/instructions
{
  "application_id": "…", "environment_id": "…",
  "text": "Test loyalty points calculation with bill amounts below, equal to and above the configured minimum bill amount.",
  "test_types": ["ui"],                                   // ui | api | responsive | audit
  "options": { "rules": [ { "name": "minimum_bill_amount", "value": "500", "description": "No points below this amount" } ] }
}
// 202
{ "id": "…", "status": "analysing", "analysis": null, "validation": null, "clarification_questions": [], … }
```

### 5.1 Statuses

`received → analysing → analysed | needs_clarification | failed`, then `approved` or `cancelled`.

| Status | Meaning | What to do |
|--------|---------|------------|
| `analysing` | The worker is working on it. | Poll. |
| `analysed` | `validation.ready` is true. | Review and approve. |
| `needs_clarification` | Questions are open and/or a blocking issue exists. | Answer the questions, fix what the issues name, or edit the analysis. |
| `failed` | The AI call failed; `error.code` says how. Nothing partial is stored. | `POST …/analyse` to retry. |

### 5.2 The structured requirement (`analysis`)

Produced by the model under a strict JSON schema and validated again on arrival; unknown fields are rejected. The same model validates a manual edit.

```jsonc
{
  "summary": "Verify loyalty points around the minimum bill amount.",
  "feature_name": "Loyalty points calculation",
  "is_feature_identifiable": true,
  "application_context": { "application": "Storefront", "module": "Loyalty", "user_actions": ["complete a purchase"] },
  "preconditions": ["A customer account exists"],
  "test_objectives": [ { "id": "OBJ-1", "title": "Bill below the minimum", "category": "boundary" } ],   // positive | negative | boundary | edge_case | validation
  "expected_behavior": [ { "objective_id": "OBJ-1", "description": null, "source": "unknown" } ],
  "business_rules": [ { "name": "Minimum bill amount", "description": "…", "source": "unknown", "value_known": false } ],
  "validation_requirements": [], "negative_scenarios": [], "edge_cases": [],
  "required_test_data": [ { "name": "Customer account", "kind": "credential", "description": "…", "credential_role": "customer", "values": [], "source": "provided_configuration" } ],
  "dependencies": [], "constraints": [], "assumptions": [],
  "missing_information": [ { "topic": "Minimum bill amount", "why_needed": "…", "blocking": true } ],
  "clarification_questions": [ { "id": "Q-1", "question": "What is the configured minimum bill amount?", "options": [], "related_to": "Minimum bill amount" } ],
  "requires_data_changes": true,
  "mentioned_targets": [],
  "ignored_instructions": []
}
```

**No invented results.** Every expected behaviour has a `source`: `stated_in_instruction`, `provided_configuration`, `clarification_answer`, or `unknown`. With `unknown` the description must be null — an answer that guesses a result under `unknown` fails validation. Each unknown result becomes a blocking issue and a question.

### 5.3 Readiness (`validation`)

Deterministic checks, independent of the model. `ready` is true when there is no blocking issue and no open question.

```jsonc
{ "ready": false, "issues": [
  { "code": "business_rule_value_missing", "severity": "blocking", "message": "The rule 'Minimum bill amount' depends on a value that has not been provided.", "subject": "Minimum bill amount" } ] }
```

| `code` | Severity | Raised when |
|--------|----------|-------------|
| `application_not_active`, `environment_not_active` | blocking | The application is archived or deleted; the environment is disabled or deleted. |
| `feature_not_identified`, `no_objectives` | blocking | It is not clear what to test. |
| `expected_behavior_unknown` | blocking | An objective has no stated result. |
| `business_rule_value_missing` | blocking | A rule depends on a value nobody supplied. |
| `credential_missing` | blocking | A needed test account's role has no credential in the environment. Fix by adding one, then `POST …/validate`. |
| `test_data_missing` | blocking | A needed configuration value is unknown. |
| `environment_read_only` | blocking | The tests would change data; the environment is read-only. |
| `out_of_scope_target` | blocking | The instruction (or the analysis) names a URL, IP address or `localhost` outside the application's allowed domains. |
| `missing_information` | blocking | The model flagged something as missing and blocking without asking about it. |
| `possible_out_of_scope_target` | warning | A bare host name outside the allowed domains is mentioned. |
| `possible_prompt_injection` | warning | Part of the text reads like an order to the AI. It was treated as plain text; the reviewer should look closely. |
| `test_data_unspecified`, `test_data_unverified`, `no_credentials_configured` | warning | Input values not given; reliance on existing data that cannot be confirmed; no credentials at all. |

`clarification_questions` on the instruction lists the open questions: the model's own (`Q-…`) plus generated ones (`AUTO-…`) for gaps it did not ask about.

```jsonc
// POST …/{id}/clarifications
{ "answers": [ { "question_id": "Q-1", "answer": "The minimum is 500. Below it no points; from 500 upwards one point per 100." } ] }
```

Answers must refer to open questions (422 `unknown_question`). Answering a subset is allowed.

### 5.4 Approval and the plan

`POST …/{id}/approve` works only for status `analysed`. Readiness is checked again at that moment (409 `requirement_not_ready` if something changed since the analysis). The approved requirement is stored as a plan version; earlier versions become `superseded`.

```jsonc
// 201 Plan
{ "id": "…", "instruction_id": "…", "version": 1, "status": "approved", "summary": "…",
  "scope": { "feature_name": "…", "objectives": [ { "id": "OBJ-1", "title": "…", "category": "boundary", "expected_behavior": "No points are awarded.", "expected_source": "clarification_answer" } ],
             "business_rules": [ … ], "required_test_data": [ … ], "preconditions": [ … ], "constraints": [ … ], "assumptions": [ … ], "warnings": [ … ] },
  "approved_by": "…", "approved_at": "…", "created_at": "…" }
```

Approval is always a person's action. Nothing in the model's output can approve, and the response schema has no field through which it could try.

### 5.5 Usage, limits and errors

Each instruction reports `usage`: `{ llm_calls, input_tokens, output_tokens, cost_usd }`. Every provider call, including failed attempts, is counted. `cost_usd` is null unless token prices are configured.

| Status | `code` | When |
|--------|--------|------|
| 503 | `llm_not_configured` | No AI service configured. Nothing is stored. |
| 429 | `rate_limited` | Too many submissions for the organization in the window. |
| 429 | `analysis_limit_reached` | The instruction used all its analysis attempts (default 6). Edit by hand or submit a new one. |
| 429 | `budget_exceeded` | The organization's monthly AI budget is spent (only with prices configured). |
| 409 | `analysis_in_progress` | Changing or re-running while an analysis runs. |
| 409 | `invalid_state_transition`, `requirement_not_ready`, `project_archived` | Wrong status for the action. |
| 422 | `unknown_target` | The application or environment is not in this project. |
| 422 | `instruction_too_long`, `unknown_question`, `validation_error` | Input problems. |
| 403 | `insufficient_role`, `admin_required` | Not allowed to change or approve. |

A failed analysis is not an HTTP error: the instruction's `status` is `failed` and `error` holds one of `llm_timeout`, `llm_unavailable`, `llm_rate_limited`, `llm_request_rejected`, `llm_invalid_output`, `llm_refusal`, `llm_output_truncated`, `internal_error`, with a message that contains no provider text.

Audit actions: `instruction.submit|update|clarify|analysis_edit|approve|cancel`.

### 6.2 The structured test case (`content`)

One schema for cases written by the model, cases written by people, and what is stored per version. Unknown fields are rejected everywhere.

```jsonc
{
  "title": "Bill amount below the minimum",
  "description": "No points under the minimum bill amount.",
  "category": "boundary",          // positive | negative | boundary | edge_case | form_validation | navigation
                                   // | authentication | api_validation | responsive | business_logic
  "test_type": "ui",               // ui | api | responsive
  "objective_id": "OBJ-1",         // the plan objective it verifies; null = a scenario beyond the plan
  "preconditions": ["A customer is selected"],
  "test_data": [ { "name": "bill_amount", "value": "499", "description": "Bill total" } ],
  "steps": [
    { "action": "navigate", "description": "Open the billing page", "target": null, "value": "/billing", "side_effect": "none" },
    { "action": "fill", "description": "Enter the bill amount", "target": "the Bill amount field", "value": "{{data.bill_amount}}", "side_effect": "none" },
    { "action": "assert_text", "description": "Check the points shown", "target": "the Loyalty points value", "value": "0", "side_effect": "none" }
  ],
  "expected_result": "No points are awarded.",
  "expected_source": "plan_objective",     // plan_objective | configured_rule | human_specified | unknown
  "priority": "p1",                         // p0–p3
  "severity": "major",                      // critical | major | minor | trivial
  "tags": ["loyalty"],
  "dependencies": [],
  "automation_feasibility": "automatable",  // automatable | partially_automatable | manual_only
  "automation_notes": null,
  "verification": { "method": "ui_assertion", "description": "The points value shows 0." },
  "assumptions": []
}
```

- **Test case ID**: the `key` on the case (`TC-0042`), unique per project and never reused.
- **Steps** use a fixed set of actions (`navigate`, `click`, `fill`, `select`, `check`, `uncheck`, `press`, `hover`, `upload`, `wait_for`, `set_viewport`, `api_request`, `assert_*`, `observe`). `target` describes the element in words; selectors are attached later, when the browser integration has seen the page. `value` may contain `{{data.NAME}}` and `{{cred.ROLE.FIELD}}` placeholders.
- **No invented results**: with `expected_source: "unknown"` the `expected_result` must be null, and vice versa (enforced by the schema and by a database constraint). Scenarios beyond the plan are generated with an unknown result. When a person writes or changes a result, the server labels it `human_specified`, whatever source the request claims.

### 6.3 Checks on a case (`validation`)

Deterministic; run at generation, on every edit, and again at approval. `ready` is true when no issue is blocking.

| `code` | Severity | Raised when |
|--------|----------|-------------|
| `no_steps`, `no_verification_step` | blocking | No action step; no `assert_*` step (unless the case is `manual_only`). |
| `vague_step`, `step_without_target`, `step_without_value` | blocking | A step does not say what to do, on which element, or with which value. |
| `placeholder_in_step` | blocking | A step still contains the generator's `TO BE DEFINED`. |
| `missing_expected_result`, `vague_expected_result` | blocking | No expected result, or one too vague to verify. |
| `undefined_test_data`, `test_data_value_missing` | blocking | A step uses `{{data.x}}` that is not defined, or whose value is still empty. |
| `credential_missing` | blocking | A step needs a credential role the environment does not have. |
| `literal_secret_in_step` | blocking | A password-like field is filled with literal text instead of a `{{cred…}}` placeholder (allowed for negative and validation cases, where wrong input is the point). |
| `unknown_objective` | blocking | `objective_id` is not in the plan. |
| `unsupported_assumptions` | blocking | `assumptions` is not empty. Confirm them as preconditions or remove them. |
| `out_of_scope_url`, `invalid_url` | blocking | A step addresses an origin outside the environment's allowlist. |
| `action_not_allowed`, `mutating_step_on_read_only` | blocking | The environment does not permit the action, or is read-only and the step changes data. |
| `possible_duplicate` | warning | Same title or same steps and data as another case. |
| `not_in_requirement` | warning | The scenario goes beyond the approved requirement. |
| `unused_test_data`, `vague_verification` | warning | |

### 7.1 Status, verdict and cancellation

`status` is the lifecycle: `queued → running → completed`, or `failed` (the engine could not be used), `cancelled`, `timed_out`; `cancelling` while a running execution is being stopped. `verdict` is the outcome and is set when the execution ends: `passed`, `failed`, `error`, `inconclusive`, `needs_review` or `flaky` (rules in [result-validation-and-healing.md](result-validation-and-healing.md) §1).

- Result statuses: `pending`, `running`, `passed`, `failed`, `error`, `flaky`, `skipped` (no script, or the execution ended first), `blocked` (the script does not fit the environment), `needs_review` (nothing failed, but a locator was replaced during the run or the recorded steps do not support a pass).
- Each result carries `failure_category` (null for a pass), `healed` and `has_ai_suggestion`; each step carries `script_index` and `healed_from`.
- `config.healing` (`mode`: `off`, `propose`, `recover`; `max_per_case` 1–5) says what the engine does when a locator matches nothing. Default `off`.
- An execution with nothing runnable ends at once as `completed` / `inconclusive` and no job is queued.
- Cancelling a queued execution is immediate. Cancelling a running one answers `cancelling`; the case in progress becomes `error`, cases not started `skipped`.
